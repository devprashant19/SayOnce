# R4 — Data and secrets

Full detail in [../12-SECURITY-AND-PRIVACY.md](../12-SECURITY-AND-PRIVACY.md).

There are **two different lists**, and conflating them is how an agent either
leaks something private or arrives on a new machine with no instructions.

## Never committed — genuinely private

| Item | Why |
| --- | --- |
| `SPEC.md` | Your role, real contacts, real projects |
| `data/golden/golden-set.json` | Real names, real phone numbers, real updates |
| `.env`, `.env.local` | Keys |
| `ROLLBACK.md` | Deployment ids |
| `.lab/` | Lab run history; regenerated by `npm run lab` |

In `.gitignore` **and** `.vercelignore`. `npm run audit:secrets` fails if any of
them reaches the build.

## Committed but never deployed — the build's own instructions

| Item | Why it is committed | Why it is not deployed |
| --- | --- | --- |
| `CLAUDE.md`, `AGENTS.md`, `BUILD-PROMPT.md` | Every agent, on every machine, must start from the same rules | They shape the build; they do not ship in it |
| `docs/` | The implementation plan is the deliverable | Same |
| `tests/`, `SPEC.template.md` | Needed to verify, and to start Phase 0 | Same |

In `.vercelignore` only. **None of them contains a secret** — that is the
condition for being on this list, and it is worth re-checking before adding
anything to it.

## Skill-generated files

`SKILL.md`, `.claude/`, `.cursor/`, `GLOSSARY.md`, `CONSTRAINTS.md`,
`DESIGN.md`, `decisions/` — gitignored, because they belong to whichever agent
you happen to be running rather than to the project.

Install agent skills **globally** (user level, `-g`) rather than into the
project, so they never land in the app folder in the first place.

## Secrets

- Server-side only. `lib/env.ts` imports `server-only`.
- **No `NEXT_PUBLIC_` anything.** There is no value a browser needs and a server
  does not.
- Keys live in the host's dashboard, never in an uploaded file.
- After every deploy: `grep -rE "AIza[0-9A-Za-z_-]{30,}|postgres://" .next/static/` must be
  empty.

## Demo isolation

The app is public with no login, so this is the load-bearing control.

- Every row carries `dataset`: `'real'` or a **signed** demo session id.
- Session ids are signed with `DEMO_SESSION_SECRET` so a visitor cannot forge
  one.
- Every demo query filters on its own session id. **There is no query path from
  demo mode to `dataset = 'real'`.**
- Sessions expire after 24 hours.
- Demo send buttons point at placeholder numbers and addresses.

## The scrub

`lib/scrub.ts` runs **before anything is displayed, saved or logged**. OTPs,
card numbers, bank accounts, Aadhaar-style ids, passwords and API-key shapes
are masked, and the trail records *that* masking happened, not what was masked.

The unscrubbed string is never stored. `updates.raw_text` holds the scrubbed
version.

`anonymise()` additionally strips phone numbers and email addresses. It is what
`/proof` uses, and `/proof` must show **no name, no phone number, no email
address** at all.

## The trail is append-only

No `UPDATE`, no `DELETE`, ever — in the application *and* in the database. A
correction is a new row.

Hashes are computed **server-side only**. If the client could compute a hash,
anyone could forge a chain and the badge would be theatre.

## Cost and abuse

A public endpoint calling a paid model is an open invitation.

| Control | Where |
| --- | --- |
| Per-visitor daily cap | `DEMO_SESSION_AI_CAP` |
| Deployment daily cap | `DEMO_DAILY_AI_CAP` |
| Kill switch, no redeploy | `DEMO_LIVE_AI=off` |
| Input length | `spokenText` max 8000 chars, in the schema |
| Cached samples | The guided path makes zero AI calls |

Past a cap: a polite message that offers the cached samples. Not an error, not
silence.

## Third-party risk

Do not use the unofficial Wispr SDK (patches the desktop app) or any unofficial
WhatsApp library (can get a number restricted). `wa.me` and `mailto:` are
official, free and cannot get an account banned.
