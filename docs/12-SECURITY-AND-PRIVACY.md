# Security and privacy

SayOnce handles the two things people are most careful with: who said what
about whom, and phone numbers. It also ships as a public link with no login.
Those facts together set the bar.

## What never leaves this machine

| Item | Why | Enforced by |
| --- | --- | --- |
| `SPEC.md` | Your role, your real contacts, your real projects | `.gitignore`, `.vercelignore`, `audit-secrets.mjs` |
| `data/golden/golden-set.json` | Real names, real phone numbers, real updates | `data/golden/.gitignore`, `.vercelignore`, `audit-secrets.mjs` |
| `.env`, `.env.local` | Keys | `.gitignore` |
| `ROLLBACK.md` | Deployment ids | `.gitignore`, `.vercelignore` |
| Real contacts and real updates | They are not demo data | `dataset` column; demo queries cannot reach them |
| `.lab/` | Lab run history, regenerated by `npm run lab` | `.gitignore` |
| Skill-generated files | `SKILL.md`, `.claude/`, `GLOSSARY.md`, `CONSTRAINTS.md`, `DESIGN.md`, `decisions/` — they belong to whichever agent you run, not to the project | `.gitignore` |

## What is committed but never deployed

`CLAUDE.md`, `AGENTS.md`, `BUILD-PROMPT.md`, `docs/`, `tests/` and
`SPEC.template.md` shape the build rather than shipping in it, so they are in
`.vercelignore` — but they **are** committed, because every agent on every
machine has to start from the same rules.

**None of them contains a secret.** That is the condition for being in this
group, and it is worth re-checking before adding anything to it.

Install agent skills **globally** (user level, the `-g` option most installers
offer) rather than into the project, so no `SKILL.md` or `.claude/` folder lands
in the app's folder in the first place.

## Secrets

- **Server-side only.** `lib/env.ts` imports `server-only`, so a client
  component that reaches for a secret is a build error, not a leak.
- **No `NEXT_PUBLIC_` anything.** There is no value in this app that a browser
  needs and a server does not.
- **Keys live in the host's dashboard**, never in a file that gets uploaded.
- **Verify after every deploy**: `grep -rE "AIza[0-9A-Za-z_-]{30,}" .next/static/` must come
  back empty. `npm run audit:secrets` does this and more, and exits non-zero on
  a finding so it can gate a deploy.

## Output scrub

`lib/scrub.ts` runs **before anything is displayed, saved or logged**.

A spoken update sometimes carries something that should never be written down:
an OTP read aloud, a card number, a bank account, an Aadhaar-style id, a
password. The scrub masks all of those and records in the Trust Trail **that
masking happened** — not what was masked.

The unscrubbed string is never stored. `updates.raw_text` holds the scrubbed
version.

`anonymise()` goes further, stripping phone numbers and email addresses
entirely. It is what `/proof` uses.

## Demo isolation

The app is public with no login, so this is the load-bearing control.

- Every row carries `dataset`: the literal `'real'`, or a signed demo session id.
- Demo session ids are signed with `DEMO_SESSION_SECRET`, so a visitor cannot
  forge one and read someone else's rows.
- Every demo query filters on the session's own id. **There is no query path
  from demo mode to `dataset = 'real'`.**
- Sessions expire after 24 hours.
- Demo send buttons point at placeholder numbers and addresses, with a note
  saying real contacts are hidden.

Tested with 20 concurrent sessions in Phase D.

## Cost and abuse controls

A public endpoint that calls a paid model is an open invitation.

| Control | Variable |
| --- | --- |
| Live AI calls per visitor per day | `DEMO_SESSION_AI_CAP` |
| Live AI calls for the deployment per day | `DEMO_DAILY_AI_CAP` |
| Kill switch, no redeploy needed | `DEMO_LIVE_AI=off` |
| Input length cap | `spokenText` max 8000 characters, enforced by the schema |
| Cached samples | The guided path makes zero AI calls at all |

Past a cap: a polite message that offers the cached samples. Not an error, and
not silence.

## The Trust Trail as a security property

Hashes are computed **server-side only**. If the client could compute the hash,
anyone could forge a chain and the badge would be theatre.

`trail_entries` is append-only in the application *and* in the database. The
Phase 4 tamper test deliberately defeats the database rule by editing a row as
the table owner — that is the point: it proves "Verify trail" turns red at
exactly the altered row.

## What a judge can and cannot do

| Can | Cannot |
| --- | --- |
| Open the app with no sign-in | See any real contact, update or message |
| Run the five sample updates | Exceed the live-AI caps |
| Type their own update and get live drafts | Affect another visitor's session |
| Open WhatsApp and email links | Message a real person |
| Read `/proof` and the latest lab run | See a name, phone number or email on `/proof` |
| Export a demo Trust Trail | Edit a trail entry undetected |

## Pre-submission audit

Run all of this, and fix every finding, before the link goes in the submission:

```bash
npm run verify:all
npm run lab
npm run audit:secrets
grep -rE "AIza[0-9A-Za-z_-]{30,}|postgres://" .next/static/ || echo clean
```

Then by hand:

- [ ] Click every link and button on landing, app, `/demo` and `/proof` at 360 px and 1440 px
- [ ] Confirm `/proof` shows no name, phone number or email
- [ ] Confirm the deployed site and its source maps contain no key, no real
      number, no real address
- [ ] Confirm `SPEC.md`, the golden set and the agent instruction files are not
      in the uploaded file list
- [ ] Check the Open Graph preview by pasting the link into WhatsApp

## Third-party risk

One thing to avoid specifically: `whatsapp_voice_transcription` and tools like
it use an **unofficial WhatsApp library that can get a number restricted**.
SayOnce uses `wa.me` links, which are official, free, and cannot get an account
banned. Do not swap them for a library, however convenient the automation looks.
